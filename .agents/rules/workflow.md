# Workflow Rules

## Goal Loop

Codexとの作業ループは、次の順序で進める。

- Codexと会話して、実装または改善したい内容をgoalとして整理する。
- 会話内容の要点を議事録として `docs/notes/yyyymmdd-hhnn-note.md` に保存する。
- 現在有効な仕様と達成条件を `goal.md` に書く。
- goalの履歴を `docs/goals/yyyymmdd-hhnn-goal.md` に保存する。
- ユーザーが承認した場合のみ、`goal.md` の内容をCodexのgoalに設定する。
- Codexのgoalに到達したら、次のgoalについてユーザーと会話を始める。

## Plan Do Replan Done

調査または実装を始める前には、必ず作業planを立てる。

`plan.md` は使用しない。ここでいうplanは、調査や実装を進めるための作業計画を指す。

作業planは細かいTODOとして記載する。

TODOは見出しごとに分けて管理する。

各見出しには、そのTODO群をplanに含めた理由や特記事項を記載する。

TODOを完了するたびに、完了したことが分かるようにチェックする。

不要になったTODOは削除しない。不要になった理由と、不要になったことが分かる状態を記録する。

作業中に、調査結果、実装結果、制約、失敗、追加要件によってplanを変える必要が出た場合は、作業planを立て直してから続行する。

plan、do、replan、do、doneの流れは、対応する議事録 `docs/notes/yyyymmdd-hhnn-note.md` に記録する。

議事録には必ず次を含める。

- もともとのplanは何か。
- planから何を変更したか。
- planをどうして変更したか。
- planをどのように変更したか。
- 最終的にどうなったか。
- 各TODOを完了したか、不要になったか。
- 各TODO見出しをplanに含めた理由や特記事項。

## Stop And Confirm

次の問題が発生した場合は、作業を停止してユーザーに確認を取る。

- 権限問題が発生した場合。
- goalを達成できないと判断した場合。
- planした時点で、goalにたどり着けるだけの材料が集まっておらず、ユーザーへの確認が必要な場合。
- plan変更が当初のユーザーの指示から逸脱する場合。
- plan変更がユーザーの指示からは逸脱しないが、回避策が迂遠、非常にトリッキー、または影響範囲が大きくなりすぎる場合。
- plan変更中に既存仕様との矛盾を発見した場合。

停止時には、次を簡潔に説明する。

- 発生した問題。
- 現在のplanとの差分。
- 続行する場合の選択肢。
- 推奨する対応。

## File Roles

- `README.md` には、アプリの目的、コンセプト、技術的ではないドメイン知識を書く。
- `AGENTS.md` には、Codexがrulesとskillsをどのように参照すればよいかを書く。
- `goal.md` には、Codexが作業を進めるために必要な目的、要件、達成条件だけを書く。
- `docs/notes/` には、検討経緯や意思決定の背景を書く。
- `docs/goals/` には、過去のgoalを保存する。
- `plan.md` は使用しない。

## Source Of Truth

- `goal.md` は作業サイクルごとに変わる現在値として扱う。
- 重要事項は `goal.md` ではなく `.agents/rules` または `.agents/skills` に書く。
- 恒久的に守るべき重要事項は `.agents/rules` に書く。
- 繰り返し使う作業手順、コマンド、チェックリストは `.agents/skills` に書く。
- 検討経緯や意思決定の背景は `goal.md` ではなく議事録に書く。
